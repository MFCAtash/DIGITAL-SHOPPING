# ADR-003: نشست کوکی (HttpOnly) به‌جای JWT

- **وضعیت:** پذیرفته‌شده
- **تاریخ:** ۱۴۰۵/۰۸/۲۶ (۲۰۲۶-۱۱-۱۷)

## زمینه
مرحلهٔ ۲ ورود با OTP پیامکی می‌خواهد. فرانت (Next.js) و API پشت **یک دامنه** (Caddy) هستند.

## گزینه‌ها
1. **JWT در localStorage/هدر:** ساده برای کلاینت‌های موبایل؛ اما قابل‌سرقت با XSS، ابطال سخت (نیاز به لیست سیاه)، و رفرش‌توکن دارد.
2. **JWT در کوکی:** همان کوکی، ولی ابطال و چرخش را خودمان بسازیم.
3. **نشست جنگو (کوکی HttpOnly، SameSite=Lax) + CSRF** (انتخاب‌شده).

## تصمیم
نشست جنگو با کوکی `HttpOnly`، `SameSite=Lax` و `Secure` در prod. نوشتن (POST/PUT/PATCH/DELETE) با کوکی ⇒ هدر `X-CSRFToken` الزامی (ninja `django_auth`)؛ توکن از `GET /auth/csrf` در JSON می‌آید پس کوکی CSRF هم `HttpOnly` می‌ماند. پس از ورود، `login()` شناسهٔ نشست را عوض می‌کند (جلوگیری از session fixation) و توکن CSRF تازه در پاسخ برمی‌گردد. سبد مهمان با کوکی امضاشدهٔ جدا (`cx_cart`).

## پیامدها
- (+) توکن از دسترس JavaScript خارج است؛ ابطال سمت سرور فوری (logout/حذف نشست).
- (+) هیچ کلید JWT برای چرخش/نشت وجود ندارد.
- (−) کلاینت‌های غیرمرورگری (اپ موبایل بومی) باید کوکی را نگه دارند یا بعداً مسیر توکن جدا (ADR جدید) اضافه شود.
- (−) نیازمند یک دامنهٔ مشترک (یا تنظیم دقیق CORS با `credentials`) و ارسال `credentials: "include"` از فرانت.
- ریسک: SSR فرانت باید کوکی کاربر را به API منتقل کند (فقط برای صفحه‌های کاربری؛ کاتالوگ عمومی بی‌نیاز).

## بازنگری
هنگام ساخت اپ موبایل یا API عمومی شریکان.
