# ADR-001: معماری Django + Next.js (و بستن مسیر Supabase)

- **وضعیت:** پذیرفته‌شده
- **تاریخ:** ۱۴۰۵/۰۸/۲۴ (۲۰۲۶-۱۱-۱۵)
- **تصمیم‌گیرندگان:** مالک پروژه
- **جایگزین‌شده توسط:** —

## زمینه

پروژه دو مسیر معماری ناسازگار داشت:

1. **Supabase + Next.js** (نقشهٔ راه phase8): احراز هویت، دیتابیس و منطق سفارش در Supabase (RLS، RPC).
2. **Django + Next.js** (بستهٔ final-8): بک‌اند Django با Postgres، ادمین، `AuditLog`، سفارش اتمی و ماشین حالت.

ادامهٔ هر دو مسیر هم‌زمان یعنی دو منطق پول و دو مدل داده و دو مجموعهٔ تست. باید یکی انتخاب شود.

وضعیت کد در لحظهٔ تصمیم:

| موضوع | Supabase | Django |
|---|---|---|
| منطق پول (عدد صحیح، تومان، تخفیف) | فقط SQL/تایپ‌اسکریپت پراکنده | `apps/pricing/money.py` با تست خالص |
| ثبت سفارش اتمی (قفل ردیف، idempotency) | ننوشته | `place_order` + تست هم‌زمانی |
| ماشین حالت سفارش | ننوشته | `states.py` با تست خالص |
| حسابرسی (AuditLog فقط‌افزودنی) | ننوشته | آماده |
| ادمین عملیاتی | ننوشته | Django admin |
| OTP پیامکی ایرانی | نیازمند Edge Function سفارشی | مسیر روشن (مرحلهٔ ۲) |

## گزینه‌ها

### الف) Supabase
- مزیت: BaaS آماده (auth، storage، realtime).
- عیب: OTP پیامکی ایرانی و درگاه‌های پرداخت داخلی را باید با Edge Function بنویسیم؛ منطق مالی در SQL سخت‌تر تست می‌شود؛ وابستگی به سرویس خارجی (دسترس‌پذیری و تأخیر برای کاربر ایرانی)؛ میزبانی داخلی دشوار.

### ب) Django + Next.js (انتخاب‌شده)
- مزیت: منطق حساس مالی در یک جا و با تست؛ ادمین آماده؛ مدل سفارش و موجودی از قبل نوشته شده؛ کنترل کامل میزبانی (Docker روی هر سرور)؛ اکوسیستم بالغ برای صف (procrastinate)، OTP و درگاه.
- عیب: ما مسئول احراز هویت و عملیات هستیم؛ بک‌اند و فرانت دو زبان متفاوت دارند (با قرارداد OpenAPI و تایپ تولیدشده مدیریت می‌شود).

### ج) Next.js با API Routes و Prisma
- مزیت: یک زبان.
- عیب: بازنویسی همهٔ منطق موجود؛ ادمین و AuditLog از صفر؛ بیشترین هزینهٔ مهاجرت.

## تصمیم

**Django + Django-Ninja + PostgreSQL** برای بک‌اند و **Next.js (App Router، TypeScript)** برای فرانت.

- مسیر Supabase **بسته** می‌شود: `overlay/supabase/` به `legacy/supabase/` منتقل شد و فقط مرجع تاریخی است.
- اپ تک‌فایلی phase8 تا آماده‌شدن Next.js زنده می‌ماند و کامپوننت‌به‌کامپوننت پورت می‌شود (مرحلهٔ ۳).
- Redis فعلاً لازم نیست: صف با procrastinate روی همان Postgres، کش با ISR.

## پیامدها

- (+) یک منبع حقیقت برای پول، موجودی و سفارش.
- (+) CI، تست و استقرار یک‌دست.
- (−) باید OTP، سبد، API سفارش و پرداخت را خودمان بسازیم (مرحلهٔ ۲ و ۳).
- (−) فایل‌های `legacy/supabase/*` و بخش‌های Supabase در نقشهٔ راه قدیمی منسوخ‌اند؛ هر تغییر جدید فقط در Django.
- قرارداد فرانت و بک‌اند: OpenAPI تولیدشده از Ninja؛ تایپ‌های فرانت با `openapi-typescript` ساخته می‌شوند.

## بازنگری

اگر پس از مرحلهٔ ۳ هزینهٔ نگه‌داری احراز هویت و پرداخت از مزیت‌ها بیشتر شد، این ADR با ADR جدید بازبینی شود (نه ویرایش).
